1Asymptotic notations

We do not care that an algorithm takes 3n2 + 5n + 2 steps. We care that it grows like n2. Asymptotic notation is the language for saying exactly that.

Why this, and why not something else
Why we do this

Two algorithms for the same job can differ by a constant factor or by an entire order of growth, and only the second kind matters once the input gets large. Asymptotic notation throws away everything that does not survive growth, so you can compare algorithms without ever running them.

Why not just do the simpler thing?

“Why not just time both programs?” Because a timing measures your laptop, your language and your compiler as much as the algorithm — and it only tells you about the input sizes you happened to test. An n2 algorithm can beat an n log n one on 50 items and lose catastrophically on 50 000. The notation predicts the crossover; the stopwatch cannot.

What goes wrong if you skip it

You optimise the wrong thing. Shaving a constant factor off an n2 algorithm feels productive and is almost worthless next to replacing it with an n log n one — and you will not know which you are looking at without the notation.

Definition of Θ
0 ≤ c1g(n) ≤ f(n) ≤ c2g(n)   for all n ≥ n0
θ(g): squeezed between two multiples of g. You must supply c1, c2 and n0 to prove it.

The proof that gets asked
To show 3n2 + 5n + 2 = θ(n2): for n ≥ 1 every term is positive so the sum is ≥ 3n2, giving c1 = 3. And 5n ≤ 5n2, 2 ≤ 2n2, so the sum is ≤ 10n2, giving c2 = 10 with n0 = 1.
Worked example — proving 3n2 + 5n + 2 = θ(n2)
To prove θ you must produce three concrete constants: c1, c2 and n0, and show the inequality holds for every n ≥ n0.
  1. Lower bound — find c1for n ≥ 1 every term is positive, so 3n2 + 5n + 2 ≥ 3n2  →  take c1 = 3
  2. Upper bound — replace each term by a multiple of n2for n ≥ 1:  5n ≤ 5n2  and  2 ≤ 2n2
  3. Add them up3n2 + 5n + 2 ≤ 3n2 + 5n2 + 2n2 = 10n2  →  take c2 = 10
  4. State the thresholdboth inequalities needed only n ≥ 1, so n0 = 1
  5. Sanity-check at n = 103(100) = 300  ≤  352  ≤  10(100) = 1000  ✓
With c1 = 3, c2 = 10, n0 = 1 the definition is satisfied, so the function is θ(n2). Notice the 5n and the 2 never mattered — only the leading term survives.

2Recurrence relations

A recursive algorithm describes its own running time. Solving the recurrence turns that self-reference into a closed form.

Why this, and why not something else
Why we do this

A recursive function describes its own cost in terms of itself, which tells you nothing useful until you unfold it. Solving the recurrence converts that self-reference into a plain formula in n that you can actually compare against another algorithm.

Why not just do the simpler thing?

“Why not just run it and see?” Same objection as before — you learn one machine and a handful of input sizes. “Why learn three methods?” Because each fits a different shape: iteration suits T(n−1), a recursion tree suits T(n/2) where you want to see where the work sits, and the characteristic equation is the only one that handles two recursive terms.

What goes wrong if you skip it

You guess the answer from the shape of the code and guess wrong. T(n) = 2T(n/2) + n and T(n) = 2T(n−1) + 1 look similar on the page and are n log n and 2n respectively — the difference between instant and never.

Iteration / substitution

Expand the recurrence a few times, spot the pattern, then write the general term.

Recursion tree

Draw the work done at every level, add up each level, then sum the levels.

Characteristic equation

For linear recurrences such as an = 5an−1 − 6an−2, solve r2 − 5r + 6 = 0.

Worked example
T(n) = T(n−1) + n  ⇒  T(n) = n + (n−1) + … + 1 = n(n+1)2 = θ(n2)
Solved by iteration: just keep expanding until you hit the base case.

Recursion tree — watch the work add up

Below, T(n) = 2T(n2) + n. Each level does the same total work, and there are log2 n levels — which is exactly where n log n comes from.

Then use the two initial conditions to pin down A and B.
Worked example — solving T(n) = T(n − 1) + n by iteration
With base case T(1) = 1. The method is simply to expand the recurrence repeatedly until the pattern is obvious, then sum it.
  1. Expand onceT(n) = T(n−1) + n
  2. Expand again, substituting for T(n−1)= [T(n−2) + (n−1)] + n = T(n−2) + (n−1) + n
  3. And once more= T(n−3) + (n−2) + (n−1) + n
  4. Spot the pattern and run it down to the base caseT(n) = T(1) + 2 + 3 + … + n = 1 + 2 + … + n
  5. Sum the arithmetic series= n(n+1)2 = n2 + n2
  6. Check at n = 71+2+3+4+5+6+7 = 28, and 7 × 82 = 28  ✓
T(n) = θ(n2). This is exactly the cost of insertion sort in the worst case — each of n insertions may shift every element already placed.

3Master theorem

A lookup table for divide-and-conquer recurrences. Compare the work the recursion creates against the work done outside it.

Why this, and why not something else
Why we do this

Divide-and-conquer recurrences nearly all have the same shape, so rather than drawing a recursion tree every time, the Master theorem reads the answer off a comparison between two quantities: how much work the recursion creates, and how much you do outside it.

Why not just do the simpler thing?

“Why not always draw the tree?” You can, and for three standard cases it is wasted effort — the theorem is the tree, already summed. But the tree is not optional knowledge: when f(n) sits between two cases without being polynomially separated, the theorem simply does not apply, and the tree is your only route.

What goes wrong if you skip it

You apply it to a recurrence it does not cover and get a confident wrong answer. T(n) = 2T(n/2) + n log n looks like Case 2 and is not — n log n is not θ(n), and the gap is only logarithmic, so no case fits. The real answer is θ(n log2 n).

The form it must be in
T(n) = a T(nb) + f(n)    compare  f(n) against nlogb a
Here a is how many subproblems you make, b is how much smaller each one is, and f(n) is the cost of splitting and recombining.
Pick a recurrence:
CaseConditionResultMeaning
1f(n) grows slowerθ(nlogba)the leaves dominate
2f(n) matchesθ(nlogba log n)every level costs the same
3f(n) grows fasterθ(f(n))the root dominates
When the Master theorem does not apply
If f(n) sits between two cases without being polynomially separated from nlogba — for example T(n) = 2T(n2) + n log n — none of the three cases fits and you must use a recursion tree instead.
Worked example — applying the Master theorem to T(n) = 3T(n/4) + n2
Match the recurrence to the standard form T(n) = aT(n/b) + f(n), then compare f(n) against nlogb a.
  1. Read off the parametersa = 3 subproblems, b = 4 (each a quarter the size), f(n) = n2
  2. Compute the critical exponentlog4 3 = ln 3ln 4 ≈ 0.7925, so the recursion side is n0.7925
  3. Compare the twon2 grows faster than n0.7925, and polynomially so (the gap is n1.2075)  →  Case 3
  4. Check the regularity condition Case 3 requiresa·f(n/b) = 3(n4)2 = 3n216 ≤ c·n2 with c = 316 < 1  ✓
  5. Apply Case 3T(n) = θ(f(n)) = θ(n2)
T(n) = θ(n2). The root dominates: the three subproblems shrink so fast that all the recursive work together still costs less than the single n2 done at the top.

4P–NP complete problems

Some problems we can solve quickly. Some we can only check quickly. Whether those two sets are the same is the biggest open question in computer science.

Why this, and why not something else
Why we do this

Some problems have no known fast algorithm, and it matters enormously whether that is because nobody has been clever enough yet or because none exists. NP-completeness lets you show that your problem is as hard as thousands of others that very capable people have failed to crack — which is a real result, not an admission of defeat.

Why not just do the simpler thing?

“Why not just keep looking for a fast algorithm?” Because once you prove the problem NP-complete you know that finding one would solve every problem in NP at a stroke. That changes the engineering decision: stop searching for an exact fast method and switch to approximation, heuristics, or exploiting special structure in your actual instances.

What goes wrong if you skip it

You burn months chasing a polynomial algorithm that almost certainly does not exist — or, in the other direction, you reach for a heuristic on a problem that was in P all along and accept an approximate answer you never needed to.

P

Solvable in polynomial time. Sorting, shortest path, matrix multiplication.

NP

A proposed answer can be verified in polynomial time, even if finding one seems hard. Sudoku, Hamiltonian cycle, subset sum.

NP-hard

At least as hard as everything in NP. Need not be in NP itself.

NP-complete

In NP and NP-hard — the hardest problems in NP. Cook–Levin proved SAT is one; everything else is shown NP-complete by reducing SAT (or a known NP-complete problem) to it.

Verifying is cheap; searching is not

For the Hamiltonian cycle problem on n vertices, checking a proposed tour costs n edge lookups. Searching all tours costs (n−1)!2.

n =8
What a reduction means
To show problem B is NP-hard, take a known NP-complete problem A and show that any instance of A can be rewritten as an instance of B in polynomial time. If you could solve B quickly you could solve A quickly — so B is at least as hard.
Worked example — verifying is cheap, searching is not
The Hamiltonian cycle problem on n = 10 vertices: does a cycle exist that visits every vertex exactly once?
  1. Someone hands you a proposed toura list of 10 vertices in order, claimed to be a valid cycle
  2. Check it — this is the verification stepconfirm all 10 are distinct, then confirm each of the 10 consecutive pairs is an edge → about 10 lookups
  3. Now suppose nobody hands you one, so you search exhaustivelyfix a starting vertex and permute the rest: (n−1)!2 = 9!2 = 362 8802 = 181 440 tours
  4. Scale it up to n = 2019!2 ≈ 6.1 × 1016 tours — at a billion per second that is over two years
  5. State what this does and does not showit shows this particular method is hopeless, not that no fast method exists — that is precisely the open question
Checking cost 10 steps; searching cost 181 440. That gap — easy to verify, seemingly hard to find — is the P vs NP question.

5Satisfiability problem

Given a Boolean formula in conjunctive normal form, is there an assignment making it true? This is the problem Cook and Levin proved NP-complete — the root of the whole family.

Why this, and why not something else
Why we do this

SAT is the problem Cook and Levin proved NP-complete first, which makes it the root of the entire family: every other NP-complete problem is shown so by reducing SAT (or something already reduced from it) to that problem. Understanding SAT is understanding where all the other hardness proofs come from.

Why not just do the simpler thing?

“Why not just try every assignment?” For 3 variables that is 8 rows and entirely reasonable. For 100 variables it is 2100 — more than the number of atoms in the observable universe. “Then is SAT useless in practice?” No — modern solvers routinely handle millions of clauses through clever propagation and learning. Worst-case exponential does not mean typical-case hopeless.

What goes wrong if you skip it

You assume all SAT is equally hard. 2-SAT is solvable in linear time through an implication graph; 3-SAT is NP-complete. One extra literal per clause is the entire difference, and not knowing which one you have means either wasted effort or a wrong complexity claim.

A 3-variable CNF formula
(x1 ∨ x2) ∧ (¬x1 ∨ x3) ∧ (¬x2 ∨ ¬x3)
Conjunctive normal form: an AND of ORs. Every clause must be satisfied.
step 0 of 0

2-SAT is easy

Every clause (a ∨ b) is the pair of implications ¬a → b and ¬b → a. Build the implication graph; it is satisfiable unless some x and ¬x land in the same strongly connected component. Solvable in linear time.

3-SAT is NP-complete

A three-literal clause has no equivalent implication between single literals, so the graph trick collapses. DPLL — assign, propagate, backtrack — is still exponential in the worst case, though modern solvers handle millions of clauses in practice.

Worked example — testing one assignment against a CNF formula
φ = (x1 ∨ x2) ∧ (¬x1 ∨ x3) ∧ (¬x2 ∨ ¬x3). Try x1 = T, x2 = F, x3 = T.
  1. Clause 1: (x1 ∨ x2)T ∨ F = T  ✓
  2. Clause 2: (¬x1 ∨ x3)¬T ∨ T = F ∨ T = T  ✓
  3. Clause 3: (¬x2 ∨ ¬x3)¬F ∨ ¬T = T ∨ F = T  ✓
  4. Combine — CNF is an AND of clausesT ∧ T ∧ T = T, so the formula is satisfied
  5. How much did that cost?3 clauses × 2 literals = 6 evaluations — linear in the size of the formula
(T, F, T) satisfies φ, so φ is satisfiable. Verifying took 6 steps; finding this assignment among the 8 possibilities is the hard direction — and with 100 variables there would be 2100 of them.

6Searching and sorting problem

The most studied problems in the subject, and the cleanest place to see a lower bound proved.

Why this, and why not something else
Why we do this

Sorting and searching are the two operations that appear inside almost everything else, so a constant-factor improvement here pays off across an entire system. They are also the cleanest place in the subject to see a lower bound proved — a statement about what no algorithm can ever do.

Why not just do the simpler thing?

“Why not always use quicksort, it is fastest in practice?” Its worst case is n2, it is not stable, and on adversarial or already-sorted input it degrades badly — which is why library sorts are usually hybrids. “Why not always use counting sort, it is linear?” Because it needs small integer keys and O(k) extra space; on arbitrary objects it does not apply at all.

What goes wrong if you skip it

You search an unsorted array with binary search. It will not error — it will confidently return “not found” for elements that are present, because the whole method rests on the ordering being there.

Binary search — halving the space

Why no comparison sort can beat n log n

The information-theoretic bound
2h ≥ n!  ⇒  h ≥ log2(n!) = Ω(n log n)
A comparison sort is a binary decision tree. It must have at least n! leaves, one per possible ordering, and a binary tree of height h has at most 2h leaves.

Beating the bound
Counting sort, radix sort and bucket sort run in linear time because they never compare two elements — they use the key values directly as array indices. The Ω(n log n) bound only binds comparison sorts.
Worked example — why no comparison sort can beat n log n
The argument is about information, not about any particular algorithm. Sorting n = 8 distinct items.
  1. Model any comparison sort as a decision treeeach internal node asks one yes/no question (“is a < b?”); each leaf is one final ordering
  2. Count the leaves the tree must haveevery one of the n! possible orderings needs its own leaf → at least 8! = 40 320 leaves
  3. A binary tree of height h has at most 2h leaves2h ≥ 40 320
  4. Take logsh ≥ log2(40 320) ≈ 15.3, so h ≥ 16 comparisons in the worst case
  5. Generalise using Stirling's approximationlog2(n!) = θ(n log n)  →  every comparison sort is Ω(n log n)
At least 16 comparisons are needed to sort 8 items, by any comparison-based method whatsoever. Counting and radix sort escape this only because they never compare two elements — they use the key values directly as indices.
